1. What Is JobMesh?

A production-style distributed job queue where clients submit background tasks via REST API. Jobs are stored in PostgreSQL, queued in Redis, and processed by independent worker services with retry logic, exponential backoff, and dead letter queues.

The One-Liner Pitch

"I built a distributed job queue system following the producer-consumer pattern. The API server accepts jobs via REST, persists metadata in PostgreSQL, enqueues IDs in Redis, and independent workers process them with exponential backoff retries and a dead letter queue for permanent failures."

4. Technology Stack

PostgreSQL

What: Relational database

Where: Docker container jobmesh-postgres-1 on port 5432

Why: ACID compliance, native JSON support, enums, industry standard

Stores: All job metadata permanently

Redis

What: In-memory data store

Where: Docker container jobmesh-redis-1 on port 6379

Why: Sub-millisecond queue ops, BRPOP blocking, atomic pops

Stores: Only job IDs (temporary queue)

Express

What: HTTP framework for Node.js

Where: API server process

Why: Industry standard, minimal, huge ecosystem

Prisma

What: ORM (Object-Relational Mapper)

Where: CLI at dev time, client at runtime

Why: Schema-first, auto-generated client, migrations

Docker

What: Containerization platform

Where: Your machine / cloud servers

Why: Portable, consistent, easy scaling

ioredis

What: Redis client for Node.js

Where: API + Worker processes

Why: Auto-reconnect, Promises, battle-tested

9. Interview Questions & Answers

System Design

Q: Explain your project architecture.

It follows the producer-consumer pattern. The API server accepts job submissions via REST, saves metadata to PostgreSQL, and pushes job IDs onto a Redis list. Worker processes independently BRPOP from the queue, fetch job details, execute the work, and update the status. PostgreSQL is the source of truth for durability, Redis is the fast channel for work distribution. Workers scale horizontally — adding more increases throughput linearly.

Q: Why use both PostgreSQL AND Redis?

They solve different problems. PostgreSQL provides durable, ACID-compliant storage — job data survives crashes and is queryable. Redis provides sub-millisecond queue operations with blocking waits. Using only PostgreSQL means wasteful polling. Using only Redis means losing data on crash. Together they complement each other.

Q: How does your system handle failures?

Three levels: (1) Job failures are retried with exponential backoff — 2s, 4s, 8s delays. (2) After max retries (default 3), the job moves to a Dead Letter Queue with the error preserved. (3) Infrastructure — if Redis goes down, the API still saves jobs to PostgreSQL. The API crashes if PostgreSQL is unreachable because it can't function without the database (fail fast).

Q: How do you scale the system?

Workers scale horizontally with docker-compose --scale worker=10. Redis BRPOP is atomic — each job goes to exactly one worker, no duplicates. API and workers scale independently based on their own bottlenecks.

Q: What is exponential backoff?

A retry strategy where wait time doubles after each failure: 2s, 4s, 8s, 16s. Prevents overwhelming an already struggling downstream service. Used by AWS SDKs, Google APIs, and most production systems.

Q: What is a Dead Letter Queue?

Where jobs go after exhausting all retries. Dead jobs are preserved with error messages, queryable via API, and can be manually retried after fixing the root cause. It's an observability and debugging tool.

Express & HTTP

Q: What is middleware?

A function that runs between receiving a request and executing the route handler. express.json() parses JSON bodies. Middleware runs in registration order — sequence matters. It can modify req/res, end the cycle, or pass to the next middleware.

Q: Why separate server.js and index.js?

App/server separation pattern for testability. Tests import server.js to get the app without starting a real server — no port conflicts, no hanging processes.

Database

Q: What are database migrations?

Version-controlled, incremental schema changes. Prisma generates SQL migration files. Teammates run prisma migrate deploy and get the same schema. CI/CD applies migrations during deployment. Complete audit trail of every change.

Q: Why UUIDs instead of auto-incrementing IDs?

UUIDs are globally unique — no collisions in distributed systems. Auto-increment IDs are predictable (security risk) and conflict when multiple databases exist.

Q: What is the Singleton Pattern for database connections?

Each PrismaClient opens a connection pool (5-10 connections). If every file created its own client, you'd exhaust the database connection limit. Our singleton creates one client shared by all files.

Redis & Queues

Q: How does Redis work as a queue?

Using Lists with LPUSH (add left) and BRPOP (blocking pop right) = FIFO order. BRPOP is blocking — workers sleep with zero CPU until Redis wakes them when a job arrives. No polling.

Q: Why store only job IDs in Redis?

Redis uses expensive RAM. UUIDs are tiny (~36 bytes). PostgreSQL already has the full data. If Redis crashes, only the queue is lost — job data in PostgreSQL is safe.

Q: What prevents two workers from processing the same job?

BRPOP is atomic. Redis's single-threaded execution guarantees each element is returned to exactly one consumer. No locks or coordination code needed.

Docker

Q: Explain Docker layer caching.

Docker caches build layers. We copy package.json before source code — so npm install is cached when only code changes. Saves 1-3 minutes per build.

Q: Dockerfile vs docker-compose.yml?

Dockerfile builds ONE image (recipe for your app). docker-compose.yml orchestrates MULTIPLE containers (API + DB + Redis + workers). One is a recipe, the other is the full meal plan.

Q: How do containers communicate?

Docker Compose creates an internal network. Containers find each other by service name — API connects to postgres:5432, not localhost. Port mapping makes services accessible from the host machine.

10. Commands Cheat Sheet

# Development
npm run dev                            # API with auto-restart
npm run worker                         # Start one worker
WORKER_ID=w1 node src/worker.js        # Named worker

# Docker
docker-compose up -d postgres redis    # Start DB + queue
docker-compose up -d --scale worker=3  # Everything + 3 workers
docker ps                              # List containers
docker-compose down                    # Stop all
